## 自动报告尚未覆盖的限制

**整帧 GPU 的来源需要进一步确认。** 六档分别有 53/38/40/39/39/39 个低于 1 ms 的正值，这些值的中位数仅 0.035–0.045 ms；8K Hard/PCF 占 7.80%/7.72%。极低值出现间隔的中位数为 0.251–0.262 秒，除 2K Hard 外，所有相邻极低值间隔均落在 0.20–0.30 秒。

这一周期与 [记录窗口](../../../Editor/Tools/VSMBaselineRecorderWindow.cs)每 0.25 秒 Repaint 一致，**疑似 Editor 窗口重绘的 GPU 计时混入整帧数据**，尚未通过隔离实验确认因果。GPU Recorder 与 FrameTiming 本来就不同步，不能只因某一行 Allocate 大于整帧 GPU 就断定该阶段计时错误。当前 comparable 检查识别正值/新时间戳/覆盖率，没有证明这些整帧结果全部对应 Game 渲染帧。低于 1 ms 仅用作诊断分组，不是自动删除阈值，原统计未重过滤。详见 [计时诊断](timing-diagnostics.json)。

**8K 是超预算运行。** 两档末帧均为 256 个驻留、491 个请求、235 个溢出；这只是末帧实测，不能推算整个窗口的溢出持续时间或阴影错误比例。8K 可作固定 256 页预算下的压力参考，不能作为“8K 请求全部驻留”的质量对照。原始 JSON 有计数，但人类可读报告没有显示页计数，也未把溢出列入 issues，因此 `completed/comparable` 只表示当前计时规则通过。

**复现范围仍有限。** 只有一轮顺序扫描，revision 为空，未保存独立厂商驱动版本和采集时源码哈希；manifest 的 review HEAD 不能追认为采集版本。快照不包含全部动态 caster、VT 内容或中间状态。GC 为整个 Editor 帧的值，不用于断定 VSM 自身分配。InvalidateStatic、UnityCompatibilityRaster、ResetFeedback 的空列仍是“无样本或未执行”，不能解释为零成本。

## 对后续优化的影响

1. 优先定位和隔离周期性整帧 GPU 极低值：通过保持同一场景的重绘开关/频率对照或独立 Player 计时确认来源，不通过丢弃慢帧或按数值筛除样本制造通过结果。报告应明确显示页预算、溢出和整帧计时来源限制。
2. **Allocate 提前为首个算法优化候选。** 4K 的约 3.23 ms 已高于 Resolve 的约 1.09 ms；8K 约 16.1–16.2 ms。当前分配 kernel 为单线程 `[numthreads(1,1,1)]`，先在 4K 无末帧溢出的条件下评估 metadata snapshot / 请求遍历开销，再验证 8K 压力场景。此处是优先级依据，尚未证明某个具体循环的占比或优化收益。
3. 保留当前六档作为诊断起点，后续增加同输入、交替顺序的至少三轮复采；确认整帧计时来源后再以相同口径验收性能收益。原始过渡断层、移动相机、缺页/fallback 和超预算质量仍需单独验证。
